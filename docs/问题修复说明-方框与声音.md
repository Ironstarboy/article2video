# 问题修复说明:汉字方框 与 声音问题

> 修复日期:2026-08-27 · 版本:v0.9.2 前置修复
> 影响范围:所有渲染成片 + 预览播放器

## 一、汉字全部显示为方框

### 现象
渲染出的视频中,所有中文都显示为「□」方框;音频正常。

### 根因(排查结论,三重叠加)
不是字体文件问题,也不是 Chrome 问题(均做过独立验证:同一批字体在 Chrome 中单独加载渲染正常)。

1. **JS 注入崩溃(主因)**:DeepSeek 偶发把定性文本(如「大幅提升」)写进数据帧的 value 字段,构建器未防御直接拼进 JS → 整段脚本崩溃 → 时间线从未注册 → 渲染器**不等待字体加载**就开始截帧 → 全部帧方框
2. **静态服务器 MIME 错误**:hyperframes CLI 0.8.15(已是最新版)内置静态服务器把一切资源按 text/html 下发(字体/JS/MP3 全如此),Chrome 严格 MIME 校验会拒绝字体与脚本
3. **字体加载竞态**:渲染器截帧不等待字体就绪(24MB+ 字体解码需数秒)

独立验证证据:
1. 服务器上直接用 Chrome 打开 `@font-face` 测试页(绕开 hyperframes 服务器)→ 字形正常(墨量 18-27%)
2. 渲染成片抽帧测量 → 字形带呈「空心矩形」特征(内部墨量仅 5%,真字形应 15%+)
3. curl 该服务器的字体/JS/MP3 响应头 → 全部 `content-type: text/html`

### 修复方案
在 composition 生成阶段彻底绕开该服务器:

1. **字体子集化 + base64 内嵌**:每个任务按其实际用字,用 fontTools 把 4 个字体裁剪为子集并转 WOFF2,以 data URL 直接内嵌进 HTML 的 @font-face —— 字体不再经过任何服务器,体积从全量 54MB 降至每任务约 1MB
2. **gsap 内联**:把 gsap.min.js 内容直接内嵌进 HTML `<script>` 标签,不再外链
3. 渲染命令增加 `--browser-timeout 300`(页面含内嵌字体,加载稍慢)

### 验证
- 生成的 index.html 含 4 段 `data:font/woff2;base64` ✓
- 待草稿渲染完成后抽帧复测字形墨量(目标 ≥15%)

## 二、声音问题

### 现象
用户反馈「视频没有正常解说声音 / 声音错误」。

### 排查结论(两个独立原因)
1. **预览播放器默认静音**:hyperframes play 页面生成的 `<hyperframes-player>` 标签自带 `muted` 属性,预览时默认无声。修复:后端代理重写 HTML 时去除 muted 属性。
2. **配音引擎链路健壮性**:此前部分帧因 TTS 服务重启窗口/短文本(<15 字)等原因回落到 edge-tts 或静音占位。已彻底移除 edge-tts(用户要求),并:
   - TTS 合成失败自动重试 3 次(2s/4s/6s 退避)
   - 分析校验门强制每帧旁白 ≥15 字(消除短文本崩溃)
   - 任务状态显示逐帧引擎追踪(cosyvoice3×N)

### 验证
- 最近三次构建配音引擎均为 `cosyvoice3×N`,零回落
- 成片 ffmpeg volumedetect:mean ≈ -29dB、max ≈ -1dB(正常解说电平)
- 待草稿渲染后再次验证音轨

## 三、附加修复(同一轮)

- **Studio 编辑器「未启动」**:`hyperframes preview --background` 是 CLI 托管会话,包装进程立即退出导致进程存活检测误判;且孤儿 preview 进程占满端口槽。修复:按端口可达性判定存活、启动脚本清理孤儿进程、访问时懒自愈、启动超时延长至 90s 且失败不阻塞构建。

## 补充:最终修复与验证(2026-08-27)

三重修复:①数据帧 value 强制数字校验 + 模板层非数字走静态文本(JS 注入防御);②字体子集化+base64 内嵌 @font-face(绕开 MIME);③gsap 内联 + 时间线注册推迟到 document.fonts.ready(渲染器等待字体)。

实测验证:1m28.8s 成片抽 3 帧做笔画宽度分布分析,粗笔画占比 91-94%(方框只有 1-2px 细边)→ 真字形确认;音轨 -29.6dB/-0.5dB 正常。

附「TTS 最小长度」:真实边界约 8 字(依分词,6-7 字必败);校验门放宽到 ≥8 字,失败自动补句号重试,无需 Qwen3-TTS。
