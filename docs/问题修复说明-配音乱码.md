# 问题修复说明:配音「读音完全不正常、断断续续」

> 修复日期:2026-09-12 · 版本:**v2.3**
> 相关提交:`a647521`(修复)、`b0102ab`(版本记录)
> 影响范围:所有走本地 CosyVoice3 的配音。数字人播报视频与 PPT 成片**同源**(同一批
> `vo_NN.mp3`),所以两者一起坏;v2.2 及更早交付的成片均受影响
> 相关工具:`server/voice_check.py`(本次排查沉淀下来的内容级抽检)

## 〇、结论速览

`tts-venv` 里的 **transformers 是 4.57.3**,而 CosyVoice3 的语音 LLM 只在官方锁定的
**4.51.3** 上解码正确。4.52+ 的 Qwen2 实现会让 speech token 序列乱掉,合成出「像人声
但内容是乱码」的音频;钉回 4.51.3 后配音立刻恢复正常。

最坑的地方:这类坏音的**时长、音量、静音比例全部正常**,当时已有的两层验收
(时长窗口 + 非静音)一条都拦不住。

## 一、现象

- 用户反馈:数字人播报视频「读音完全不正常、断断续续」
- 客观化之后是这样(whisper 对当时某帧配音的听写):

  | 台词(期望) | 实际听写 |
  |---|---|
  | 毛泽东同志指出,问题就是事物的矛盾…… | 也不是背住了我脖子皮皮膀一找他付出这笔包我再替他打算以因此的捕 |
  | 发展新质生产力要因地制宜…… | 一老衙铺,第一衣是最配衣啊然後我大大地铺吃飽我在陪伴…… |

- 但同一批音频的客观指标:

  | 指标 | 数值 | 判定 |
  |---|---|---|
  | 时长 / 预期(字数÷4.2) | 0.84 – 0.88 | ✅ 落在验收窗口 0.65–1.8 |
  | 峰值 | -2 dBFS | ✅ 远超静音下限 -40 dBFS |
  | 语音窗占比 | 37.7% | ✅ 与正常语音一致 |

**结论:所有「非内容」指标都健康。** 这类故障只能靠内容级判据发现。

## 二、第一步:先确认坏在哪一段(不是播报拼接)

v2.2 刚修过播报音轨的字节对齐 bug,所以第一件事是排除「拼接又坏了」:

| # | 检查 | 方法 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | 播报音轨 vs 各帧源配音 | 逐帧解到 44.1k 单声道做互相关(按 ffprobe 真实片段起点对齐) | **11/11 帧 r = 1.000,lag = 0** | 音轨拼接完全忠实,没问题 |
| 2 | ASR 本身是否可信 | whisper 听写**参考音频** `asset-v2/male.wav` | 内容 100% 正确 | ASR 与参考音频都正常 |
| 3 | 源配音内容 | whisper 听写 5 条真实台词配音 | **5/5 全乱码** | **坏在源配音**,与播报/成片无关 |

判定依据(第 1 项的命令,节选):

```bash
# 播报音轨与源配音逐帧互相关:r≈1 表示音轨就是源配音的忠实拼接
ffmpeg -v error -i renders/avatar.mp4 -vn -f f32le -ac 1 -ar 44100 pipe:1 > bc.f32
ffmpeg -v error -i assets/audio/vo_02.mp3     -f f32le -ac 1 -ar 44100 pipe:1 > vo02.f32
# 再对两者做 FFT 互相关(完整判读路径见 §十)
```

> 顺带确认了一个容易被忽略的事实:成片与播报视频**共用同一批 `vo_NN.mp3`**,
> 所以「播报坏、成片好」这类判断在这套架构里不成立 —— 要么一起好,要么一起坏。

## 三、第二步:构造「可懂度」反馈环(本次排查的关键)

已有的验收维度拦不住,就先造一个能红的判据,否则任何修复都无法验证。

**做法**:whisper(small)听写 → 与台词做**最长公共子序列(LCS)占比**(先繁简归一)。

- 判合格线取 **0.70**;实测:正常样本 **0.83–0.97**;乱码样本 **≤ 0.20** —— 区分度极大
- 成本:一段 15 秒音频约 4 秒(含模型常驻);模型 `small` 约 461MB,一次性下载

这个判据已沉淀成仓库工具 `server/voice_check.py`(既能被后端当**抽检**调用 —— 结果写
`job.state.voice_check`,阈值取很宽只提示不阻塞;也能手工跑):

```bash
TTS_PY=/data/Avatar/tts-venv/bin/python
WHISPER_DIR=/tmp/ttv_dbg/whisper        # whisper 模型缓存目录(--model-dir)

# 抽检某任务的配音(按台词长度自动挑最长的 N 帧,长句最能暴露乱码)
$TTS_PY server/voice_check.py \
    --script jobs/e868f32bec3d/project/script.json \
    --audio  jobs/e868f32bec3d/project/assets/audio \
    --frames 11 --model-dir $WHISPER_DIR
# → {"checked":11,"lcs":0.895,"worst":0.83,"warn":false,"samples":[...]}
```

> 繁简差异会白吃掉一截 LCS(whisper 有时输出繁体)。装了 `zhconv` 会先归一;
> 没装时正常样本也可能掉到 0.6 左右 —— 工具里因此把告警线放得很宽(0.35),
> 判定"好/坏"请看上面那组实测区间,而不是只看 `warn`。

## 四、第三步:差分实验,把坏点收敛到「语音 LLM」

CosyVoice3 的链路:

```
文本 ──text token──┐
参考音频 ─tokenizer─┴─→ 语音 LLM(Qwen2 backbone + speech_embedding)
                          │ 生成 speech token 序列
                          ▼
                     flow(CausalMaskedDiffWithDiT) → mel
                          ▼
                     hift 声码器 → 波形
```

关键动作是**在一次模型加载里把各条推理路径都跑一遍**,用输出直接切分链路:

| 调用路径 | 经过 LLM? | 输出 | 结论 |
|---|---|---|---|
| `inference_vc`(源音频→tokenizer→flow→vocoder) | ❌ | **完全正确**(「希望你以后能够做得比我还好」,就是参考音频的内容) | tokenizer / flow / vocoder **都是好的** |
| `inference_zero_shot`(官方示例原样) | ✅ | 乱码 | |
| `inference_cross_lingual` | ✅ | 乱码 | |
| `inference_instruct2` | ✅ | 乱码 | **坏的是语音 LLM 这一环** |

> `inference_vc` 这一条是分水岭:它用同一个 speech tokenizer 抽 token、同一个 flow、
> 同一个声码器,唯独不经过 LLM。它对了,就说明问题在 LLM(以及它的输入 conditioning)。

**同时被排除的假设**(每条都做了实验,不是推测):

| 假设 | 实验 | 结果 |
|---|---|---|
| 注意力实现不兼容(SDPA vs eager) | `attn_implementation=eager` 重跑 | **逐字节相同**,排除 |
| fp16 数值不稳(PPU/新 GPU) | `TTV_TTS_FP16=0` 起 fp32 实例重跑 | 同样乱码,排除 |
| GPU 算错 | matmul / conv1d / softmax / LayerNorm / SDPA(各后端)与 CPU 双精度比对 | 误差在正常范围,排除 |
| 采样参数不稳(top_p/top_k/贪心) | 贪心解码 | 更差(整段静音/退化),排除 |
| 我们的调用/prompt 写错 | 官方 `example.py` 原样跑 | 同样乱码,排除 |
| ONNX 提供者 | 本机 onnxruntime 只有 CPU provider,无从对比 | 不构成变量 |

> 这一步还顺带确认:**同一输入在同一进程/跨进程是可复现的**(固定种子),
> 所以「重采」拿到的其实是同一类坏样本 —— 这也解释了为什么 v2.2 的「重采 6 次
> 取最接近预期」只能凑时长、救不回内容。

## 五、根因

**`transformers` 版本。** 把 CosyVoice3 官方 `requirements.txt` 锁定的两项装回
`tts-venv` 后,所有路径立刻恢复:

| 对照 | transformers 4.57.3(坏) | transformers 4.51.3 + tokenizers 0.21.4(好) |
|---|---|---|
| 官方示例「八百标兵奔北坡」 | 「再剖一怎麼出二愛三等等愛三好再剖…」 | 「八百飙兵奔北坡,北坡炮兵并排跑…」(同音字误差,内容正确) |
| 工作区 `male` 参考音频 | 乱码,时长 25.6s | 7.44s,内容正确 |
| `female` / `male_narrator` | — | 7.36s / 7.48s,内容正确 |
| 时长 / 预期 ratio | 0.03× – 2.36× 乱跳(本次实测) | 0.79 – 0.95,稳定 |

**为什么一直没暴露**:

1. `BUILD.md` 第四节明确要求「不能用官方 requirements.txt」—— 官方会把 torch 降到
   2.3.1,而 RTX 5090(sm_120)根本没有对应内核,会把整个环境搞坏。这个决定本身没错。
2. 但 `tts-venv` 是用 `python -m venv --system-site-packages` 建的,于是**静默继承**了
   系统里的 transformers 4.57.3。少装的只有那两个包,报错也没有 —— 它只是「说得不对」。
3. 上一轮排查(v2.2,提交 `03a1893`)试过 fp16/fp32、采样参数、prompt 长短、
   `text_frontend`、ONNX provider、`llm.rl.pt`,唯独没有怀疑过**版本**,
   最后只能把它归因为「本机运行时/权重不稳定」并用时长验收兜底。

## 八、教训与防护

1. **配音有三类失败,三种判据缺一不可**:
   | 失败模式 | 例子 | 能拦住它的判据 |
   |---|---|---|
   | 没声音 | 静音占位(-91dB,时长却正常) | 峰值检查(v2.2 补) |
   | 时长不对 | 残句 0.04s / 复读 36.8s | 时长窗口(v2.2 补) |
   | **内容错** | 本次:乱码但时长/音量全正常 | **内容级判据(ASR/可懂度)** |
2. **依赖钉版必须落到「启动校验」**:只写在文档里的版本要求,在下一次重建环境时形同不存在。
   `--system-site-packages` 建的 venv 尤其危险 —— 它会让「少装一个包」变成「静默用了别的版本」。
3. **升级音色/模型/解码器相关的任何包之前**,先跑一次
   `server/voice_check.py`;它是唯一能在坏音上线前拦住它的检查。
4. **差分实验优先**:与其对着代码猜,不如在**一次加载**里跑遍所有调用路径,
   用输出把链路一刀切开(`inference_vc` 那条就是本次的分水岭)。

# 附二:后续(v2.8)—— 运行时修好了,成片里的配音却还是乱码

> 修复日期:2026-09-12 · 版本:**v2.8** · 现象:用户报「配音坏了非常混乱」
> 一句话:**v2.3 只修好了"新合成",没修"已经烧坏的老配音"** —— 它们被当作"可复用"
> 一直躺在任务目录里,重新构建、重新渲染都原样接着用。

## 一、现象与实测

内容级抽检(本文 §三 的判据,whisper 听写 vs 台词 LCS):

| 任务 | 配音合成时间 | 抽检 LCS(修前) | 重烧后 | 成片时长变化 |
|---|---|---|---|---|
| `5590965bf587` | 18:41 | **0.016** | **0.715** | 81s → 48s |
| `00cd61bacf07` | 04:06 | **0.006** | **0.796** | — |
| `eafca9e512a8` | 03:41 | **0.000** | **0.776** | 94s → 60s |
| `e868f32bec3d` | 20:53(v2.3 修复后) | 0.895 | — | — |

> 时长普遍变短是副作用:乱码样本的时长/预期 ratio 乱跳(1.3–3.4×),旧成片是按
> 那批"长坏音"排版出来的;重烧后回到自然语速,时长也就回到真实值。

## 二、根因:v2.3 漏掉的一半

v2.3 的钉版只保证**新合成**是正确的。而配音是**按指纹复用**的:

```python
# v2.7 及以前:指纹只有 台词 + 音色 + 引擎
_vo_signature(script, voice, provider)
# 复用判断里还有一条兜底:project/script.json 与当前脚本逐帧文本一致 → 直接复用
if reuse_vo and (job.state.get("vo_sig") == sig or _built_source_matches(job, script)):
```

**运行时口径不在指纹里** → 用坏运行时烧出来的 `vo_NN.mp3`,在运行时修好之后依旧是
"指纹相符、可复用"。于是:

- 用户点「重新构建预览」→ 复用坏配音;
- 照 v2.3 §七 的产线动作点 `build?force_voice=1` 才会重烧,但没人会每次都记得加这个参数;
- 成片、播报视频同源(§二 已确认),所以一起继续坏。

## 三、修法

### 1. 结构:把"口径"算进复用指纹(`server/config.py` + `server/main.py`)

```python
# server/config.py
VO_SYNTH_VERSION = os.environ.get("TTV_VO_SYNTH_VERSION", "2")

def vo_runtime_fingerprint() -> str:
    """配音运行时口径 = 钉版依赖 + 合成版本;进 _vo_signature,变了就重新合成。"""
    deps = ",".join(f"{k}=={v}" for k, v in sorted(PINNED_TTS_DEPS.items()))
    return f"{deps};vo{VO_SYNTH_VERSION}"

# server/main.py
raw = json.dumps([_frames_signature(script), voice, provider,
                  vo_runtime_fingerprint()], ensure_ascii=False)
```

**复用条件同时收紧成"指纹完全相符"**,删掉 `_built_source_matches` 兜底 ——
它的本意是"省一次 GPU",实际效果是给坏配音开了一扇门。

效果:换模型、改解码参数、改验收口径、换钉版……旧配音自动作废,**普通的「构建预览」
就会重烧**,不依赖使用者记得加 `force_voice=1`(实测:不加参数直接 `POST /build`,
进度直接进"配音合成中")。

### 2. 检测:可懂度抽检接进流水线

`server/voice_check.py` 由构建流程在**每次真正重新合成之后**自动跑一次(默认 2 帧),
把结果写进 `state.voice_check`;`warn=true` 时预览页弹红条 + 「重新合成配音」按钮。

- 只提示不阻塞:whisper 不可用 / 超时 / 异常一律跳过,构建照常
- 阈值 0.35(好样本实测 0.6–0.99,乱码 ≈0),whisper 模型缓存默认 `models/whisper`
- 复用(未重烧)时不跑 —— 省时间,且复用的音频上一轮已经抽检过

## 四、教训(补 §八)

5. **"修好运行时"不等于"修好产物"**:凡是被缓存/复用的产物(配音、数字人片段、抠像遮罩),
   复用指纹里必须包含**产生它的口径**(模型 / 运行时 / 参数版本 / 合成版本号)。
   否则这类修复只对新任务生效,老任务会带着坏产物一直"看起来正常"。
6. **修复必须带回收动作**:改完代码,受影响的历史产物不会自己变好。本次按 §七 的动作
   对三个任务做了重烧 + 重出成片/播报,并用抽检复核(0.016/0.006/0.000 → 0.715/0.796/0.776)。
7. **兜底复用要写清代价**:`_built_source_matches` 那种"文本一致就复用"的兜底,省下的是
   几分钟 GPU,赔上的是"坏产物永久复用"的可能 —— 这类兜底应当只在**产物口径已知**时开。
