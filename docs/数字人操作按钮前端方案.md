# 数字人操作与预览的前端方案

> 问题:后端已经把数字人做成一条**可生成、可缓存、可叠加**的能力,但网页上只有创建期的一个勾选框。
> 进入分析结果面板之后,数字人**没有任何状态、没有任何按钮、没有任何可以看的东西**;
> 渲染完也没有一句话确认人像到底叠上去没有,而且**纯 PPT 版成片在叠加成功的那一刻被就地销毁**
> (`main.py:249` 的 `composed.replace(out)`),用户永远拿不到它。
>
> 目标:在分析结果面板里,把 HyperFrames 与数字人做成**两条并列可见的轨道**,依赖关系画在明处,
> 并交付两个各自的产物 —— **纯 PPT 版**与**含数字人的最终版** —— 在用户点击「叠加」后合成一条最终下载。
>
> 前置阅读:`ARCHITECTURE.md` 第七节(数字人链路)、`CONTEXT.md`(术语表)、
> `docs/adr/0001`(预览里为什么看不到数字人)、`docs/adr/0002`(圆角投影为什么在叠加时完成)。
> 姊妹文档:`docs/数字人前端方案.md` —— 那篇讲**信息呈现**,本篇讲**操作与预览**。
> 本篇是本轮拷问后的定稿,取代此前的同名草稿。

### 1.4 一个必须先纠正的隐含假设:**脚本时长是过期的**

设计任何"按帧"的操作之前必须知道的事实,也是本方案最容易做错的地方。

| 事实 | 证据 |
|---|---|
| `tts.apply_real_durations()` 只改**内存对象**,不回写 `jobs/<id>/script.json` | main.py:158;tts.py:275-331 |
| `assemble.build()` 顺手把**调整后的**脚本写进 `project/script.json` | main.py:160;assemble.py:254-257 |
| 前端轮询拿到的 `j.script` 来自 `job.paths()["script"]`,即**没调整的那份** | jobs.py:65-78、104-105 |

实测同一个任务(已渲染、已叠加):

```
jobs/<id>/script.json   durations = [7,     9.14,  10.29, 10.29, 10.29, 5   ]
project/script.json     durations = [5,     13.77, 18.83, 12.96, 10.19, 3   ]  ← 权威
avatar_timeline.json    start     = [0,     5.0,   18.77, 37.6,  50.56, 60.75]
```

**结论:前端绝不能用手里的 `script.frames[].duration` 推算数字人的起点或"该帧时长"。**
帧级数字人信息只能由后端从 `project/avatar_timeline.json` 给出。

> 附带发现(本方案顺手修):帧表的"时长"列现在显示草稿时长,与成片不符。P0 一并换成权威值。

### 1.5 三条必须知道的流水线事实

| 事实 | 证据 | 对设计的影响 |

### 1.7 纯 PPT 版今天存在过,但被销毁

`stage_render` 的顺序(`main.py:227-257`):

```
hyperframes render --output renders/out.<fmt>   ← 纯 PPT 渲染,写到磁盘
composite_onto_video → renders/out_avatar.<fmt> ← 叠加产物
composed.replace(out)                           ← 纯 PPT 版被覆盖,永久消失
（失败时 composed.unlink,out 保持未叠加 —— 这一版反而被留下了）
```

实测:`jobs/*/project/renders/` 下三个任务**都只有 `out.mp4`**,没有任何 `out_avatar` 残留。
所以"提供纯 PPT 版下载"**不是新建一条渲染链路,而是停止销毁一个已经有的产物**。

### 1.8 渲染的磁盘预检过于悲观(不是磁盘不够)

`logs/backend.log:1158` 记着唯一一次被记录的渲染尝试失败于 `capture_disk`:

```
may need ~51956.1 MB of temporary frame storage, but only 45960.5 MB is free
at /data/Avatar/jobs/e868f32bec3d/project/renders/work-<uuid>/captured-frames
```

该任务实测:`jobs/e868f32bec3d/project/script.json` 是 **13 帧、成片 208.8 秒**。
这个估算来自 HyperFrames 自己的预检(源码 `dist/cli.js`):

```js
function estimateDiskCaptureBytes(totalFrames, captureOptions) {
  const scale = captureOptions.deviceScaleFactor ?? 1;
  const outputWidth  = Math.ceil(captureOptions.width  * scale);
  const outputHeight = Math.ceil(captureOptions.height * scale);
  return Math.ceil(totalFrames) * outputWidth * outputHeight * 4;   // ← 未压缩 RGBA
}
// 判定:estimatedBytes <= freeBytes * 0.9 才放行
```

`6264 帧(208.8 秒 × 30fps) × 1920 × 1080 × 4 字节 = 51,956.1 MB` ——
**与报错原文 51956.1 MB 逐位吻合**,证实这就是它的公式。**它按"每帧一张未压缩位图"估算,完全不计实际落盘格式。**

而实际落盘格式由**输出容器**决定,与内容无关(同源码):

```js
frameExt: needsAlpha ? "png" : "jpg"            // 实际写盘格式
needsAlpha = outputNeedsAlpha(config.format)     // MOV/WebM → png;mp4 → jpg
```

实测 `jobs/5590965bf587/project/assets/` 下**只有 5 个 mp3,没有任何视频或 alpha 源**。所以:

| 口径 | 208.8 秒成片 |
|---|---|
| 预检估算(未压缩 RGBA) | **51,956 MB ≈ 50.7 GiB** ← guard 用的就是这个 |
| 实际落盘(MP4 → JPEG 帧) | **~1.5 GB** |
| 实际落盘(MOV/WebM → PNG 帧) | ~12.5 GB |

**预检对 MP4 幻灯片虚高约 33 倍。** 静态门槛 = `51956/0.9 ≈ 57,729 MB ≈ 56.4 GiB`;
当时 `/data` 空闲 45,960 MB,对 guard 而言只有 41,364 MB 可用额度,于是被拦下。
**当前 `/data` 空闲 43,837 MB,仍然过不了这个门槛** —— 这就是它至今没跑起来的原因。

**为什么它这么保守**:guard 必须在渲染**开始前**判断会不会中途撑爆,而帧的实际大小不可预测;
对 MOV(ProRes 4444 + alpha)那几十 GB 是真的。宁可多要,也不要在渲染第 20 分钟时炸。

### 1.9 真正的机制:`--workers` 默认 auto 让流式编码失效,于是撞上 guard

三条实测串起来的因果链(不是推断):

**一、流式编码的闸门是"只有一个 worker"**(源码 `dist/cli.js`):

```js
function shouldUseStreamingEncode(cfg, outputFormat, workerCount, durationSeconds, forceParallelStream) {
  if (cfg.enableStreamingEncode === false) return false;
  if (outputFormat === "png-sequence" || outputFormat === "gif") return false;
  if (durationSeconds > cfg.streamingEncodeMaxDurationSeconds && !cfg.lowMemoryMode) return false;
  if (forceParallelStream) return true;
  return workerCount === 1;            // ← 关键
}
```

日志实测(不传 `--workers` 时):

```json
{"streaming-encode gate": {"enabled": false, "configFlag": true,
  "outputFormat": "mp4", "workerCount": 5,
  "durationSeconds": 208.8, "maxDurationSeconds": 240}}
```

`configFlag: true` 说明流式本就是默认允许的,但 `workerCount: 5` 让它 `enabled: false`
→ 走**落盘**路径 → 撞 precheck → **渲染在写第一个字节前自杀**。

**二、precheck 只挡落盘路径。** 实测直接跑 `hyperframes render --format mp4 --quality high`:

```
退出码 1   墙钟 29 秒   /data 峰值消耗 78 MB   renders/ 峰值 1 MB
阶段: compile 660ms · audio 8342ms · 标定 15928ms → capture_disk 抛错
```

29 秒全花在准备上,**一帧都没写盘**。所以这是个成本前置的保护,不是"渲染到一半撑爆"。

**三、`--low-memory-mode` 之所以能救,是因为它把 worker 钉成 1**,顺带打开了流式闸门 ——
不是因为它"省内存"。加 `--low-memory-mode` 后(同项目、同参数):

```
退出码 0   墙钟 308 秒(5m08s)   产物 14.4 MB · 208.8 秒视频
/data 峰值消耗 78 MB   ← 流式路径确实不落盘
日志: "Streaming frame 6264/6264"、"static-dedup reused 2592/6264 frame(s) (41%)"
```

**结论:落盘捕获(`--workers auto` → 5)与磁盘 guard 是天生冲突的一对。**
在一台 43 GiB 空闲的机器上,`--workers 1`(或等价的 `--low-memory-mode`)是唯一可行的配置。

**顺带更正两条此前的误判**:
- 写盘位置是 `project/renders/work-*/captured-frames`,**就在 `/data` 上**,不是系统盘。
  `/tmp/hyperframes-extract-cache-*` **从未存在过**;`--frames-cache-dir` /
  `HYPERFRAMES_EXTRACT_CACHE_DIR` 这些"提取缓存"参数服务的是**源视频抽帧**
  (日志里 `videoCount:0, totalFramesExtracted:0` —— 本项目没有源视频),**与本问题无关**。
- 因此"边界 130 秒"也是错的 —— 那是把 guard 当成了真实占用。

**按实际 JPEG 占用推算(约 7.5 MB/秒)**:100 GB 的 `/data` 足以覆盖全部支持的片长,
包括讲解档最长的 30 分钟(约 13 GB)。真实约束是**预检门槛**(208 秒的片子就要 56 GiB 空闲),
不是磁盘容量。

`/dev/vda1 49G → /`(剩 15 GB)与本问题无关,但值得记一笔:任何我们自己的临时文件都**不要**落 `/tmp`。

## 二、思路校正:两处需要改

你的模型是:分析完脚本 → 构建视频那边,**HyperFrames 的纯 PPT 渲染预览和生成下载**,**同步**生成数字人,
**渲染 ffmpeg 合并到最终结果**。三处与代码相符,一处是术语问题,一处需要改。

| 你的说法 | 代码事实 | 处理 |
|---|---|---|
| 纯 PPT 渲染预览和生成下载 | 它今天**存在过又被销毁**(1.7) | ✅ 采纳:停止销毁 + 给下载入口 |
| 同步生成数字人 | 片段生成必须等配音(1.5),物理上不能与构建并行 | ⚠️ **改**:见下 |
| ffmpeg 合并到最终结果 | 这一步叫**叠加**,发生在渲染之后(ADR-0001) | ⚠️ **术语**:见下 |
| 数字人和 HyperFrames 并列展示 | 两者在状态、产物、缓存键上都是独立的一套 | ✅ 采纳:这正是当前 UI 最缺的东西 |

### 2.1 术语:「合并」不是「叠加」

`CONTEXT.md` 把**成片**定义为"PPT 视频**与各帧数字人片段叠加后**的最终输出文件" ——
所以"叠加"和"最终结果"是同一件事的动词与名词,不是三步。

而"合并"在本仓另有含义:`deploy/verify-avatar.py` 里"校验合并后成片"、以及音视频合流,
指的是**合流成可下载文件**。

**取「叠加」为唯一说法,「合并」列入 `_Avoid_`。** 顺带把 `out_avatar.<fmt>` 这个只活了几毫秒的中间名一起去掉(1.7)。

### 2.2 「同步」改成什么

你要"同步"的动机是**更快拿到最终结果**。但实测(1.8)显示:

- **瓶颈不在 CPU 也不在磁盘容量,而在磁盘预检**(1.8):MP4 幻灯片的实际落盘只占预检估算的约 1/33;
- `--workers` 已经是 `auto`(CLI 默认,`main.py:232-233` 未覆盖),渲染自己已经吃满了并行;
- `composite_onto_video` **只调用 ffmpeg**(libx264 CPU 编码 + 一张已缓存的遮罩 PNG),
  它和 Chrome 渲染**技术上可以并行**(`avatar.py` 里没有任何锁,两者同在 `RENDER_SEM` 的 2 个槽位内),
  但两个 CPU 大户同时跑会互相拖慢,收益是几十秒,在 5-20 分钟面前是噪声。

**所以本方案不做并发改造,而是把"同步"落到三件真正有效的事上**(详见第十节):
产物分离、发布步骤合并、以及启用 GPU 编码(见第十节)。

## 三、设计原则

1. **操作跟着状态走,不铺开成一排。** 没开数字人 → 一个字都不显示(与既有任务界面完全一致);
   开启后才有区块;失败后才出现补救按钮。绝不做一排常年半灰的按钮。
2. **降级必须可见。** 数字人失败可以出普通成片,但必须在**用户做决定的那个现场**说出来。
3. **区分"生成片段"与"叠加成片"**,这是两个成本、两个条件、两个失败原因的动作。
   按钮文案必须让用户知道自己在触发哪一个、要不要重新渲染。
4. **复用既有形状。** 单文件 vanilla JS、无构建:芯片就加芯片、帧表就加列、按钮就加按钮。
   弹层是本方案唯一的新范式,只允许出现一个。
5. **不暴露用户已经决定不要的东西。** 形象固定(金立),不做形象选择器;
   换图是运维动作,留接口不留 UI。
6. **跨阶段状态必须落到任务里。** 前端要显示的帧级/服务级信息一律进 `job.state`,
   不允许前端去猜、去翻文件。

```
│                                                                          │
│ ⚠ 成片早于最后一次修改:脚本在 14:32 改过,成片是 14:05 渲染的。           │
│   [重新渲染成片]                                     ← 产物过期时才出现  │
└──────────────────────────────────────────────────────────────────────────┘
```

### 4.2 数字人区块的六个部分

| 部分 | 内容 | 何时出现 |
|---|---|---|
| **A 状态芯片** | `出镜已开启` / `说话 a · 待机 b` / `已叠加` 三枚独立芯片,各说一个事实 | 开了数字人就出现 |
| **B 只读配置** | 形象名 + 文件名、位置、尺寸 | 常驻,灰字 |
| **C 生成进度** | `4/6 段 · 正在生成第 5 段(帧 6)` + 条 | 仅 `avatar_building` / `building` 期间 |
| **D 告警条** | 失败原因 + 补救按钮 | 仅失败时 |
| **E 主动作** | `重跑数字人片段`、`查看完整时间轴` | 常驻(按状态禁用) |
| **F 诊断折叠区** | 服务检测、缓存统计、清空本任务片段、关闭数字人出镜 | 点击 `诊断 ▸` 展开 |

**芯片为什么拆成三枚**:今天 `state.avatar` 一个布尔值承担了三个事实
("打算出人 / 已生成片段 / 已叠加"),而它已经产生了实际的状态残留 ——
`stage_build` 在 `avatar` 为假时**只删时间轴、不清** `avatar_clips`/`avatar_error`(main.py:175-176),
旧的真值会留下来。三枚芯片各对应一个可证伪的事实,前端不再拼表达式,也不会再出现
"芯片说已叠加、成片里没人"这种最难查的 bug。

### 4.3 逐帧表新增的"数字人"列

| 片段状态 | 文案 | 操作列 |
|---|---|---|
| `talking` | 说话 ✓ | `[预览]` `[重生成]` |
| `blank` | 待机 ✓ | `[预览]`(无重生成,待机片段全局共用) |
| `failed` | 说话 ✗(警示色,title 给原因) | `[预览]` `[重生成]` |
| 未生成(计划态,灰字) | 计划:说话 / 计划:待机 | `[预览]` 禁用,`[重生成]` 可用 |

判定口径与 `avatar.build_frame_clips()` 一致:有台词 **且配音文件存在** → 说话,否则 → 待机
(avatar.py:396-400)。但**状态由后端给出,前端只展示**。

列定义在 `renderScript`(L782)与 `renderEditable`(L810)**两处**,加列时两处都要改。

### 4.4 成片下载区:两个按钮并列

| 按钮 | 样式 | 条件 | 内容 |
|---|---|---|---|
| **下载最终版(含数字人)** | `.btnrow button.primary`(红实心) | `artifacts.final` 存在 | 格式 + 大小 |
| **下载纯 PPT 版(无数字人)** | `.btnrow button`(蓝框) | `artifacts.ppt` 存在 **且任务开了数字人** | 格式 + 大小 |

- **只有开了数字人的任务才出现第二个按钮**:没开数字人时两个产物是同一个文件,给两个入口就是让用户
  在两个完全相同的下载之间选择。
- 开了数字人的任务**常驻显示纯 PPT 版**,不只在失败时出现 —— 用户可能只是想看看没人像的画面。
- 两个按钮**各自显示自己的格式与大小**,不做"切换"控件:用户不需要记住自己下载了哪一个。

### 4.5 产物过期提示

纯 PPT 版与最终版都是**渲染那一刻**的快照。脚本被重新编辑或重新构建之后,它们就过期了。
这个事实今天被"两个产物都过期"掩盖着,分开之后必须说出来。

判定(无需新增后端字段):`state.rendered_at`(或 `artifacts.*.at`)早于
`job.script_updated_at` → 显示黄条 `成片早于最后一次修改` + `[重新渲染成片]`。
**不自动渲染、不自动删除** —— 过期是提示,不是动作。

### 4.6 单帧预览弹层(本方案唯一的 UI 新范式)

这个前端**没有任何弹层基础设施**:全文只有一处 `position:fixed`、一处 `z-index`
(都是 `#toast`,L200),而 `#toast` 是 `pointer-events:none` 且 3.6 秒自动消失 —— **不可交互**。
所以弹层必须从零写:遮罩、`z-index`(须 > 100 以盖住 toast)、ESC 关闭、点击遮罩关闭、
`body` 滚动锁定、加载态、错误态。

**弹层内容(一次请求一张 PNG,不做视频播放)**:

```
┌ 帧 3 的数字人效果 ─────────────────────────── [×] ┐
│  ┌────────────────────────────────────────────┐  │
│  │ [底图 + 左上角圆角投影人像]                 │  │
│  └────────────────────────────────────────────┘  │
│ 底图来源:成片(第 37.6s)   ← 或「项目快照」        │
│ 人像:说话片段 · 18.8s · 320×320                  │
│ ⓘ 底图来源为项目快照时,画面随时间变化,与成片可能有细微差异。│
└──────────────────────────────────────────────────┘
```

**底图取哪个**分三档,按优先级回退:

1. **有最终版** → `ffmpeg -ss <timeline.start> -i final.<fmt> -frames:v 1`。
   这是**最终效果**,包括真实字幕与画面。
2. **没有最终版但渲染过**(只有纯 PPT 版)→ 从纯 PPT 版抽帧,人像用当前片段叠上去。
   用户看到的是"如果现在叠加会长什么样"。
3. **完全没渲染过** → 用 `hyperframes snapshot --at=<start>` 取项目静帧,
   `--output` **必须指向临时目录,不得写进项目目录**(1.8 的坑)。
   构建完即可看,把"提前看到"从渲染之后提前到**构建之后**。

**无论哪一档都必须标明底图来源**。否则用户会把项目快照误认成最终效果 ——
这正是 ADR-0001 要避免的那类误解换个形式复发。

## 五、状态机

### 5.1 任务级

新增一个进行中状态 **`avatar_building`**,与现有三个并列:

| 状态 | 含义 | 是否计入"在飞任务" |
|---|---|---|
| `analyzing` | 文章分析中 | 是 |
| `building` | 配音 + 组装 + (数字人)片段生成 | 是 |
| **`avatar_building`** | **仅重跑数字人片段** | **是** |
| `preview` | 可预览 / 可渲染 | 否 |
| `rendering` | HyperFrames 渲染 + (数字人)叠加 | 是 |

复用会让"正在重跑数字人"被误读成"正在构建",把「构建预览」按钮按错误的语义改写文案。
**为什么计入在飞任务**:`MAX_INFLIGHT_JOBS = 4`(main.py:59)是防 GPU/LLM 被打爆的闸门
(判定在 `_inflight_count()` main.py:386 与 `:432`);
重跑数字人是分钟级 GPU 推理,不计入就等于给了一个绕过闸门的口子。
**重启处理**:`jobs.py:156-159` 会把 `uploaded/analyzing/building/rendering` 强制转 `failed`,
新增的 `avatar_building` 必须一并加入这个列表。

## 六、失败:三个现场,三套动作

后端有三个互不相同的失败点,而且**失败不会让任务失败、成片照常产出**。
三种失败的**修复动作完全不同**,所以必须在用户做决定的那个现场分别说。

| 现场 | 触发 | 文案 | 主按钮 |
|---|---|---|---|
| **数字人区块**(任务级) | 构建期整批失败 `avatar_clips=0` | `未能生成数字人片段:<原因>` + `成片仍可正常产出,只是没有数字人。` | `重跑数字人片段` |
| **数字人区块**(若原因含"不可达") | gRPC 服务没起 | `数字人服务未运行(127.0.0.1:50051)。` + 部署提示 | `检测数字人服务` |
| **帧表行内** | 逐帧级失败(需改后端) | 该行"数字人"列 `说话 ✗`,title 给原因 | `[重生成]` |
| **成片区** | 渲染期叠加失败 | `本次成片未叠加数字人:成片仍是完整的 PPT 视频。` | `重跑数字人片段` → 再`渲染成片` |

**"不可达"要单独识别**:`avatar_error` 会是 `数字人服务不可达:127.0.0.1:50051`。
这一条对用户最有用的不是"重试",而是"服务没开" —— 重试一百次也没用。

### 8.1 必须一并修的两处状态缺陷

1. **失败时不要清掉 `avatar_clips`**:现在 main.py:174 在失败时写 `avatar_clips=0`,
   会**覆盖此前成功过的计数**。改为只在真正生成成功时写。
2. **关闭数字人时清干净**:main.py:175-176 只删时间轴。补上清空
   `avatar_clips / avatar_error / avatar_frames / avatar_overlaid`。

### 8.2 配置冻结(accept 而不是 now)

`avatar_image` / `avatar_geom` 必须在**创建任务时**从当前配置取值并存在 `state` 里。
若运行时读全局配置,运维改了 `TTV_AVATAR_X` 或换了形象图,所有历史任务的展示都会跟着变,
而它们的成片里其实是旧位置、旧形象。冻结后,展示与实际永远一致。

## 十、交付、合成与提速

这一节回答"最终结果怎么交付",以及 Q9 要求的"在 5090 上找一个能正常运行、较快的配置"。

### 10.1 三个产物,一次发布

| 产物 | 中文名 | 文件名 | 生产者 |
|---|---|---|---|
| **项目** | (不是文件) | `project/` | `assemble.build()` → Studio 可预览 |
| **纯 PPT 版** | 纯 PPT 版 | `renders/ppt.<fmt>` | `hyperframes render --output renders/ppt.<fmt>` |
| (中间) | 数字人片段 | `.cache/avatar/*.mp4` | `build_frame_clips()` |
| **最终版** | 最终版 | `renders/final.<fmt>` | `composite_onto_video(ppt, timeline, final)` |

**渲染直接写 `ppt.<fmt>`**,叠加读它、写 `final.<fmt>`。
这样纯 PPT 版从渲染成功那一刻起就是**一等产物**,而不是一次 rename 的副产品 —— 对应你选的
"纯 PPT 版永不单独删除"。它也顺带消掉了 `out_avatar.<fmt>` 这个只活几毫秒的中间名。

**不做并发改造**。真正影响"5-20 分钟"的是编码配置与 `capture_disk` 预检(10.4/10.5),
不是把两个 CPU 大户塞进同一时刻。

### 10.2 路径显式记进任务(取代 `Job.video_path()`)

`Job.video_path()`(jobs.py:80-86)今天**靠 `render_format` 反推文件名**、找不到就悄悄回落到 `out.mp4`。
单产物时勉强自洽;**两个产物之后,这个反推会变成"静默给错版本"**。改为显式记录:

```jsonc
// job.state
"artifacts": {
  "ppt":   {"path": "renders/ppt.mp4",   "bytes": 6236406, "at": 1789157865.5, "fmt": "mp4"},
  "final": {"path": "renders/final.mp4", "bytes": 6236406, "at": 1789157865.5, "fmt": "mp4"}
}
```

- `path` 是**相对任务目录**的 POSIX 路径(不存绝对路径:任务目录可迁移)。
- `to_dict()` 用 `artifacts` 计算 `has_video` / `video_size`(`has_video = bool(artifacts.final)`)。
- `api_video` 增加 `?artifact=final|ppt` 参数,默认 `final`;`final` 不存在时返回 409 并附中文提示,
  **不回落**到 ppt(静默回落正是要拆掉的东西)。

### 10.3 旧任务就地迁移

磁盘上 3 个任务只有 `out.<fmt>`(`00cd61bacf07`、`5590965bf587`、`eafca9e512a8`)。
`load_from_disk()`(jobs.py:142-163)里加一次性迁移:

### 10.4 渲染配置(已实测落地)

**根因与 GPU、与磁盘容量都无关。** 真正的因果链是(见 1.9):
`不传 --workers → auto 选到 5 → 流式编码闸门要求 workerCount===1 所以关闭 → 走落盘捕获
→ 撞上按未压缩 RGBA 估算的 precheck → 在写第一个字节前失败`。

三次实测(同一项目 `jobs/e868f32bec3d`,208.8 秒 / 13 帧 / 1080p):

| 配置 | 结果 | 墙钟 | /data 峰值 | 捕获模式 |
|---|---|---|---|---|
| `--quality high`(不传 workers) | **失败** | 29 s | 78 MB | 落盘预检即抛错 |
| `--quality high --workers 1` | **成功** | **5m03s** | 78 MB | 流式(不落盘) |
| `--quality high --low-memory-mode` | **成功** | 5m08s | 78 MB | 流式(不落盘) |

后两次的闸门输出**逐字段相同**(`enabled: true, workerCount: 1`),
证明 **`--workers 1` 与 `--low-memory-mode` 等价**,而后者是更重的开关(还会切到截图捕获策略)。
产物:13.7 MB / 208.8 秒视频;`static-dedup reused ~2600/6264 frame(s)` 省了约 160 秒。
渲染结束**无 `work-*` 残留** —— 流式路径确实不落盘。

**落地配置**(已写进 `server/main.py` 的 `stage_render`):

| 配置 | 值 | 为什么 |
|---|---|---|
| `--workers` | **`1`(显式)** | 唯一能让流式编码生效的值;`auto` 在本机选 5 → 必然撞 precheck |
| `--quality` | `high`(不变) | 画质优先;要更快再降档 |
| `--low-memory-mode` | 不启用 | 与 `--workers 1` 等价且更重,无需叠加 |
| `--gpu` / `--browser-gpu` | **暂未启用** | 见下 |

**`--gpu` / `--browser-gpu` 暂不加**:实测 5 分钟的瓶颈在**捕获**(`capture_streaming` 占 279 s /
303 s),而编码只占 `assemble` 的 17 s。GPU 编码救的是那 17 秒。
要加速应当先动 `--quality`,而不是 `--gpu`。这条留作独立优化,需先有基准数据。

**不需要**注入 `HYPERFRAMES_EXTRACT_CACHE_DIR` / `TMPDIR`:那两条针对**源视频抽帧缓存**,
本项目没有源视频(`videoCount:0, totalFramesExtracted:0`)。

**教训**:`capture_disk` 的预检与"落盘捕获"路径天生绑定。任何把 worker 数交给 `auto`
的调用,在这个项目的机器规格下都会撞上它 —— 这就是这次渲染功能等于不可用的原因。

### 10.5 `capture_disk` 触发时的对策(不是默认配置)

预检在渲染开始前抛错时,按代价从低到高:

1. **腾空间越过门槛** —— 判定是 `估算 ≤ 空闲 × 0.9`,而估算是 `总帧数 × 1920 × 1080 × 4`。
   208 秒的片子需要 **~56 GiB 空闲**才放行(当前 43 GiB,过不了);
   清掉 `.cache/uv`(实测 **17 GB**,包管理器缓存)即可越过。**这只对短片有效,长片无解。**
2. **`--low-memory-mode`** —— 流式编码,峰值降到常数级;代价是钉死 1 个 worker。
3. **`--low-memory-mode` + 分片** —— 长片(讲解档)的兜底。

界面上的呈现方式见第六节:这类失败要**单独识别成"渲染环境问题"**,而不是让用户以为自己的内容有问题。

### 10.8 换数字人不重渲染幻灯片(v2.16 补)

**用户口径**("我只是想换数字人没有改文本,不应该重新渲染 hyperframes;历史上 ppt 已经生成了,
直接烧录新数字人就行了;也就改了 ppt 的样式才重新渲染")。

10.1 已经把 `ppt.<fmt>` 立成一等产物(纯 PPT 渲染,不再被叠加覆盖)—— 这一节把它**当缓存用**:

- **判定**:`main._ppt_render_signature(job, fmt)` = `sha1(口径版本 + fmt + quality + workers +
  project/script.json 摘要 + 风格组合 + 逐帧配音摘要 + BGM 摘要 + 模板/样式/组装器源码摘要)`;
  写入 `state.ppt_render`(`{sig,fmt,path,bytes,at,renders,reuses}`)。指纹相符且
  `renders/ppt.<fmt>` 在(≥10KB)→ 跳过 HyperFrames,直接进叠加;否则照旧渲染,**成功之后**
  才记指纹。
- **数字人不进指纹**:形象/位置/大小/抠像都是渲染后由 ffmpeg 叠的,换它们本来就不该重渲染幻灯片。
- **配音进指纹**:`ppt.<fmt>` 的音轨就是配音 + BGM(`composite_onto_video` 的 `-map 0:a?`),
  所以换声音(台词没变也一样)必须重渲染。
- **不拿 `index.html` 字节当指纹**:字体子集化的 woff2 每次构建都不同,产物字节会让缓存永远命不中。
- **ppt 缓存不许被改名/覆盖**(原 1.7 的"纯 PPT 版被销毁"就此彻底解决):无数字人时用**硬链接**
  把 ppt 呈现成 final(不额外占空间);写 final 前一律先 unlink(否则 ffmpeg `-y` 截断同 inode 会
  把缓存一起截掉)。顺带修掉"关掉出镜后旧 final 还在原地被当成新产物交付"的旧缺陷。
- **前端**:渲染进度第一步显示「复用历史 PPT(未重渲染)」;渲染按钮下方一个默认不勾的
  「强制重新渲染幻灯片」勾选框(`force_render:true`),怀疑历史画面不对时的逃生口。
- **回归**:`server/smoke_test.py` 新增 32 项(指纹稳定性 / 换数字人不改指纹 / 改台词改样式换配音
  换格式必改指纹 / 命中判定 / `stage_render` 复用与 force / 缓存不被写坏 / 接口 force_render 严格布尔)。

## 十四、风险与对策

| 风险 | 对策 |
|---|---|
| **用草稿时长推算帧时间轴** | 帧级信息一律由后端从 `project/avatar_timeline.json` 给出(1.4) |
| **缓存跨任务共享**,删缓存误伤别的任务 | 键里没有 job id(avatar.py:271-275),`.cache/avatar` 现有 22 个文件。`[清空本任务片段]` **只删本任务时间轴引用的那些**,不做全目录清空 |
| **gRPC 探活阻塞事件循环** | 探活后台线程 + 立即返回,结果写 `avatar_probe`,前端轮询 |
| **重跑绕开并发闸门** | `avatar_building` 计入 `MAX_INFLIGHT_JOBS`(main.py:59/432);另加 `AVATAR_SEM` |
| **状态残留导致芯片说谎** | 修 8.1 两处缺陷;三枚芯片各对应一个独立字段,前端不拼表达式 |
